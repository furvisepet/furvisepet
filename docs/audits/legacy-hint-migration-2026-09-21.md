# Hint-ranked chronological migration eligibility

Base: bb6b639c16be6dcd96a1f808ea13a34dbc4f173f.
Offline only. No paid APIs, live Ask, deployment or application changes.

## Result: no exact-equivalent Category A migration established

The new supporting allocator can protect an independently selected factual result.
It does not make existing chronological hints advisory-only retroactively.
Every legal nonempty-hint chronological shape still feeds hint-ranked rows into
the SAME factual record collection, and every such ticket adds a global partial
coverage reason. There is no legacy field marking a separate supporting subset.

Finite limits and representation pressure expose membership differences.
Redundant/non-matching hints can preserve membership on a fixture, but still fail
the requested coverage/reason parity. No classification based on a small fixture,
current ledger contents, or a hint having no current matches is safe for all data.

No migration adapter is added. The existing legacy_hint_ranking guard is retained.
Thirteen new counterexample tests and this inventory are the only changes.

## Exact algorithm at the ticketed chronological path

1. Acquire bounded owned pages: canonical subject order, asc raw traversal for a
   legacy ticket without selection, existing 4 x 64 candidate envelope.
   searchHints do not change these page queries.
2. Existing effective-history resolution, temporal/anchor window resolution and
   mandatory predicates determine matching effective rows.
3. Sort that matching set by requested chronology (event, created, stable ID).
4. Sort a copy by number of matching hints descending, then chronology. Literal
   normalized phrase matching only; multiple hints create a score hierarchy.
5. Apply finite outputs.limit globally if present.
6. Apply the existing 32-record / 18,000 note+title-character caps, omitting whole
   oversized rows and continuing. Sort survivors back into presentation order.
7. Publish those survivors as records, not as optional support. Track omitted
   matching IDs. The chronology receipt names the original chronological boundary
   and becomes blocked when that boundary was displaced or is uncertified.
8. Any nonempty hint adds bounded_period_context_not_semantic_completeness and
   forces partial status even if all candidates fit and the hints score uniformly.

Consequently final display ordering alone cannot reveal hint-induced membership
changes. Supporting allocator JSON-row budgets also differ from old note+title
character accounting; silently equating the two is not exact transport parity.

## Remaining shape classification

All ticketed rows below may have one/multiple owned subjects; arbitrary AND/OR
text predicates or none; asc/desc order; an explicit window, no window, or legal
resolved anchor. These dimensions share the same hint algorithm above.

| Shape | Cardinality and hints | Classification | Why it stays |
|---|---|---|---|
| Nonuniform hints + finite chronological limit | Global take N AFTER hint ranking; one or many hints | B MIXED | Hints can change returned factual records, boundary representation and blocking. |
| Nonuniform hints + null limit | All matching rows semantically; hint priority before hard transport limits | B MIXED | 32-row or character pressure changes represented factual membership and omissions. |
| Uniform/redundant hints, including an identical mandatory singleton predicate | Matching set/order can be unchanged | Not eligible A under full gate | Hint presence still changes factual coverage/reasons and common certificate behavior. |
| Currently non-matching hints | Same survivors on a particular dataset | B / not provably A | Another valid ledger can match; even current empty/no-match behavior retains different coverage. |
| Hints + envelope evidenceNeeds | Finite/null limits; scoped quoted independent facets | C or mixed legacy obligations | Envelope needs affect completion/support/receipts in legacy paths; no marker proves optional-only. Entire shape remains. |
| Hints + oldest-calendar-year | Calendar-dependent window plus ranking | Outside scope | Calendar behavior unchanged. |
| Hints + native selection, strategy absent | Existing grouped/global selection | Not a chronological migration candidate | Already uses common selection. No legacy strategy to remove. |
| Empty/null hints | Ordinary finite or unbounded chronological | Already migrated in prior commits | No new advisory allocation needed. |
| Non-ticket query/relevance hints | Raw-question terms, aliases, event rarity, temporal fallback and reservations | B MIXED | Hints influence acquisition and returned evidence; no typed optional-only boundary. |

There are no legal chronological + bound-needs or chronological + episode tickets:
the existing binder rejects those combinations. True grounded multi-need tickets
already run common Lungs. Do not count them as an unimplemented chronological
selector. Envelope evidenceNeeds and broader mixed/episode compatibility callers
are distinct remaining legacy classes, not permission to weaken these rules.

## Consumers and effects

history-retrieval.ts maps survivors into careEntries, represented source provenance,
requiredSourceIds, candidate accounting and chronology receipts. Downstream
ask-evidence.ts fallback boundary checks, read-projection.ts boundary projections,
Labs eligibility/snapshot construction, need coverage, prompt budgeting and
model-assisted review consume those factual collections and receipts.

No consumer receives a separate legacy supportingContext collection. Demoting
some old survivors into optional context would change their source eligibility;
keeping them in factual collections would violate the requested new invariant.
No publication authority or Labs code is altered to conceal this distinction.

## Offline witnesses and parity outcome

- Single finite selection: food hint promotes an older matching record over the
  newest. Original chronological boundary is then blocked. Native ordered take
  selects the newest; allocator may carry the older row only as non-authoritative
  support. That is intentional behavioral improvement, NOT exact parity.
- Two hints: combined score promotes another factual row. Different hints over
  the same data change old records but not common semantic selection.
- Unbounded 40-row matching set: rare oldest hint match survives the legacy
  32-row cap; common ordered result representation retains a different set.
- Two large records: character pressure yields different factual survivors.
- One-row redundant hint and no-match hint: identical records, old partial status
  and hint reason versus common complete resultSet proof. Coverage differs.
- Corrections/deletes and rotated subjects preserve the same counterexamples;
  no raw superseded/deleted candidate is manufactured by the tests.
- Optional acquisition failure leaves the independent native factual result
  unchanged; this proves the new allocator's separation, not legacy parity.

Authoritative parity: NOT established for a migrated class; none migrated.
Supporting parity: prior isolated allocation fixtures remain 26/26; no full legacy
chronological migration parity is claimed. New tests do not require the native
factual selection to change to match an old prompt. They assert the counterexample
and retained compatibility exclusion instead.

Existing publication/authority tests cover profile alternatives being rejected
for certified historical obligations; no new source permissions are introduced.

## What remains and what would be a different task

The remaining classes are:
- hint-ranked chronological factual/representation selection;
- envelope independent obligations with mixed acquisition/completion semantics;
- chronological calendar combinations;
- stored mixed-read compatibility and non-ticket legacy retrieval.

Bound needs and episodes are not legal chronological ticket combinations. Other
strategy branches remain unchanged. No old chronological branch is deleted.

The allocator supplies a representation mechanism, not proof that an old hinted
request meant latest/earliest independently of ranking. Changing legacy hint
semantics or relocating its coverage limitations would require a deliberate
semantic/coverage migration with accounted deltas. That is outside this exact-
equivalence cut. No new primitive, raw-English parser or duplicate executor is
proposed. Hint-ranked factual execution is NOT removable.
