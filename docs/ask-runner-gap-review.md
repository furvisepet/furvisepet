## Verified findings

This is a source review of [the classification](ask-runner-gap-classification.md) against the unchanged [lifetime audit](../scripts/audits/ask-lifetime-history.audit.mjs), [fixtures](../scripts/audits/fixtures/ask-lifetime-history.mjs), and [harness](../scripts/audits/helpers/lifetime-harness.mjs). The audit defines 17 tests: six controls, the repaired ordinal pet-switch test, and ten remaining requirements. **7 pass / 10 fail is a historical result**, recorded in [the subject repair report](ask-subject-continuity-repair.md), not a result obtained for this review.

The actual generation boundary is correctly identified. In [route.ts](../app/api/ask/route.ts), the `generate: async () =>` closure passes `liveContext`, authorized subject IDs, subject frame and discourse focus to [generateAskHistoryAnswer](../app/lib/intelligence/generate-ask-history.ts). That function retrieves historical candidates, retrieves episode evidence, creates the evidence contract from the resulting context, and calls [runFurviseIntelligence](../app/lib/intelligence/run-intelligence.ts). Changing only `generationInput` would not change this closure's inputs. The harness's `history: true` path calls this same function, captures the actual serialized provider input, and returns the final validated answer; it does not execute the HTTP route.

All ten claimed failures are accounted for below. “Legacy” describes an asserted representation, not permission to retire the expectation.

## Disagreements

**The ten classifications are not all correct as written.** Requirement 6 conflates three independent issues: qualified ordinal recognition, legacy record suppression on the historical path, and omitted metadata in the legacy serializer. Its claim that missing reference authority explains this fixture's behavior skips the fact that the episode-reference path is never entered. Missing authority would still require safe clarification after recognition is repaired; it is not the current execution path. Supported linked-list tests showing `sequenceNumber` and `recurrenceOf` do not establish support for this wording.

**The proposed resolution repair addresses the right final-answer boundary but does not yet specify the entire callback contract.** `askEvidenceScope` recognizes `hiding` as a requested topic, but not in its `history` predicate. For the exact Luna question, `requestKind` is `ordinary` and `readOnlyRecall` is false. No historical/episode result or fallback overrides that flag. Thus the read-only stripping block in `runFurviseIntelligence` is not activated. The fixture's empty proposals do not prove that adversarial proposed learnings, care actions or semantic writes would be suppressed. This is a missing guarantee, not evidence that a write actually occurred.

The final validator runs **after** learning/care policy evaluation, semantic governance and persistence routing. A prose-only replacement there cannot retroactively establish the proposed no-write invariant. A bounded repair needs deterministic status-question recognition before those steps, while retaining a final prose authority independent of provider recovery flags.

The suggested Luna wording also omits the date required by the proposal's own attribution rule. The fixture note is dated **2026-08-19**, while the harness clock is 2026-09-04. An acceptable answer is: “The August 19, 2026 note reports that Luna still hid sometimes. I can't establish that the hiding has ended.” This attributes the observation without claiming current persistence or current resolution. Avoid reproducing `fully resolved` in this answer, even inside a quotation or negation: the unchanged audit forbids it anywhere in the serialized answer. Preserve exact quotations for separate source-note recall requests.

Finally, “highest immediate trust impact” is a prioritization judgment, not demonstrated comparative evidence. Unsupported affirmative resolution is a reasonable bounded next repair, but missed cross-pet corrections also affect trust. Neither priority nor a disclosed limitation establishes any of the other requirements as complete.

## Repair acceptance criteria

These are requirements for a future authorized implementation; this review makes no application or test changes.

1. **Bound recognition before governance.** Recognize explicit, question-only, single-authorized-pet resolution-status recall deterministically. Include the exact Luna question and state the supported topic/wording set. Reject ambiguous subjects/topics into uncertainty; do not infer ownership from model prose. Keep mixed owner observations, explicit saves and new resolution updates outside this recall-only policy. Represent the recognized scope in the evidence contract created inside `generateAskHistoryAnswer`, so the actual callback sees it. Do not implement only in `generationInput`, a direct generator call, or a provider prompt.

2. **Make recall read-only through the returned result.** Activate the existing stripping boundary before learning/care/semantic governance for recognized status questions. Verify that later deterministic action builders and authoritative semantic frames cannot reintroduce writes. Require zero accepted care actions, learnings and semantic events, no offered history update, no mutating application actions, and no write-authorizing V2 output. Preserve permitted read/navigation actions and ordinary update behavior. Do not change persistence machinery to compensate for an answer-validation patch.

3. **Use bounded, represented evidence.** Evaluate same-owned-pet, same-topic source evidence with source identity, observation date and explicit qualifications. Bind the answer to the final budgeted representation, not all loaded notes or provider context IDs. The recent path does not supply historical source-version/correction revalidation: do not claim it does. Missing, omitted, stale, ambiguous, conflicting or unrevalidated evidence permits an uncertainty answer, never a certified present resolution. If bounded revalidation is necessary, specify its row, character and time limits before implementation and preserve existing historical limits; do not introduce an unbounded legacy-note scan. Never populate complete coverage or verified facts merely to bypass the current policy.

4. **Own the complete answer at validation.** For this narrow scope, deterministically compose a nonempty attributed/uncertain answer covering title, summary, section headings/items and safety note. Clear inconsistent follow-ups and references. Partial improvement remains partial; a dated terminal owner report may be described as historical evidence without becoming verified current medical status. Do not use a generic forbidden-string substitution, infer lifecycle transitions or depend on provider recovery flags. Preserve urgent/emergency guidance and shopping suppression. Preserve source-quote and authoritative episode rendering order for requests outside this scope; a status question must not acquire episode-reference authority.

5. **Exercise the actual callback with adversarial mocks.** Add loader -> `generateAskHistoryAnswer` -> captured actual prompt -> final-result cases, using the existing synthetic harness and network block. Keep the exact lifetime fixture and its expectations unchanged. Assert `care:luna-hiding` is represented, its date/qualification survives into the grounded response, and the forbidden phrase is absent from the whole answer. Inject affirmative claims separately in title, summary, section heading/item and safety note; vary recovery flags and proposed writes, including a supplied authoritative semantic frame. If invalid terminal flags trigger the existing provider retry path, test bounded retry behavior separately instead of weakening the lifetime harness's one-call assertion.

6. **Add meaningful boundary controls.** Cover partial improvement, dated owner-reported resolution, no evidence, wrong pet, wrong topic, ambiguous wording, deleted/changed/superseded sources, omitted evidence and unavailable revalidation. Exercise both recent and supported historical paths where applicable. Assert uncertainty rather than absence when evidence is unavailable. Include urgent questions and genuine new owner updates as controls. Preserve existing source quotations, subject switches, validated episode lists, displayed ordinal identity and stale-reference rejection.

7. **Keep repair accounting honest.** This repair targets requirement 7 only. For a later requirement-6 repair, separately test “second episode” and “second soft-stool episode” through the actual callback, with and without an owned envelope; distinguish stored sequence from displayed ordinal and retain all original record/metadata assertions. Requirements 1–5 and 8–10 remain open under the bounds in the table: no selector-cap increase, inferred correction edge, prose-derived authority, note-count aggregate or uncertified arithmetic shortcut is acceptance. Future verification must run the unchanged lifetime audit and applicable evidence/history/episode/subject and repository checks in an authorized local environment, report actual results and unexpected changes, and preserve all expectations. Do not predict an 8-pass/9-fail result before running it.

## Limitations

Only source and test definitions were inspected. No audits, application tests, providers, database operations or other external services were run. Test-case references describe assertions, not fresh passing results. The precise requirement-6 failure boundary is a source-derived conclusion, not a newly captured stack trace. The harness replaces provider/database dependencies and some conversation helpers; it does not verify HTTP orchestration, persistence, production data, installed migrations, permissions, timing or snapshot consistency. Historical retrieval itself declares `read_committed_no_snapshot`.

AGENTS.md was read. This task writes documentation only, so no Next.js implementation guidance was needed. Only `docs/ask-runner-gap-review.md` was added; the classification, audit, fixtures, expectations and application remain unchanged. No credentials, dependencies, other worktrees, commits, pushes, merges or deployments were used.
