# Live Ask diagnostic workflow

Use the existing main Chrome test-account session and existing server diagnostics. This tooling does not authenticate, read cookies, call a provider, create/delete accounts, access an admin database, or retry requests. The historical admin smoke scripts are outside this workflow.

1. Verify idle ownership, resources, current production alias/deployment/commit and the designated test account. Record the Waraich job ID and immutable script hash. Reconcile the existing cumulative live budget and unresolved calls; approval does not reset spending. Do not submit if accounting or authorization is unknown.
2. Prepare one fresh question. Keep its text in the test console only; receipt tooling stores its SHA-256. Write a pinned preparation input with `runId`, `questionSha256`, `deployment` (`id`, `commit`, `origin`, `target`, `state`), `deploymentEvidenceSha256`, `jobId`, `jobScriptSha256`. Deployment origin must be `https://www.furvise.com`, target `production`, state `READY`. `prepare` adds the actual local HEAD, dirty state, full tracked/untracked file manifest, index hash and status hash. Store outputs OUTSIDE the repo so evidence cannot change the tested manifest.
3. Recheck the deployment immediately before dispatch. For `mark-dispatched`, pin the prepared plan file and supply the reconciled budget evidence. `capMicrodollars` cannot exceed the original $1 ceiling; this script does not renew authority. `authorityExpiresAt` represents the existing live-test authority, never a manufactured expiry or the expired recovery policy; use null only when the reviewed original live authority specifies no expiry. Unknown authority or accounting leaves the plan prepared. The immutable intent and global prompt fence precede the one browser submission. Any interruption after either fence remains consumed/uncertain; never rename or replay it.
4. Submit exactly once through the normal Ask UI. Capture the actual logical-turn and attempt IDs from the request/trace, HTTP response status from the browser network record or matching request log, and the visible result separately. A provider's 400 and the route's 503 are different statuses. Never infer HTTP status from visible prose or an MCP console event.
5. Collect only the matching request's existing server provider events, schema rejection diagnostic, turn/credit settlement and provider reservation/reconciliation records. Use exact deployment and request identifiers with bounded time filters. No unrelated user logs. Do not read a service-role key. Hash imported evidence and preserve its original receipt; never copy raw provider bodies, credentials, schema literals or private answer text into diagnostic reports.
6. `collect` joins matching request/attempt/deployment records into one immutable receipt. Missing fingerprints, phases or accounting stay explicitly incomplete. Uncertain cost is `null`, never zero. A complete diagnostic is NOT product acceptance. Check that source/index/deployment identity still matches and retain Waraich's final job_result with the same evidence.

Commands (Node 24, cwd is the Furvise checkout):

```powershell
node scripts/audits/ask-live-diagnostic.mjs prepare OUT INPUT INPUT_SHA256
node scripts/audits/ask-live-diagnostic.mjs mark-dispatched OUT DISPATCH_INPUT DISPATCH_INPUT_SHA256
node scripts/audits/ask-live-diagnostic.mjs collect OUT COLLECT_INPUT COLLECT_INPUT_SHA256
```

Dispatch input: `planPath`, `planFileSha256`, and `budget` containing `complete`, `uncertainCalls`, `unreconciledCalls`, `evidenceSha256`, `usedMicrodollars`, `reservedMicrodollars`, `nextMaximumMicrodollars`, `capMicrodollars`, `authorityExpiresAt` (epoch milliseconds or reviewed null). These are reviewed evidence, not authority granted by this utility.

Collection input: `planPath`, `planFileSha256`, `evidence`. Evidence contains `logicalTurnId`, `attemptId`, `deploymentId`, `questionSha256`, `providerEvents`, `response`, `accounting`. Every provider event, response and accounting record must repeat the same request/attempt/deployment identities from authoritative correlation records; do not fabricate missing mappings. Provider events use `phase`, `outcome`, optional sanitized `providerError`, `inputTokens`, `outputTokens`. Response uses actual `httpStatus` and optional fixed `code`. Accounting uses `providerCallCount`, `creditState`, `settlementState` and unique `calls` with `callNumber`, `reservedMicrodollars`, `actualMicrodollars`, `state` (`reconciled`, `pending`, `uncertain`).

Reuse `safeAskProviderErrorDiagnostic` and `withAskProviderSchemaDiagnostic`. Imported sanitized schema metadata is hash-pinned server evidence; importing JSON does not recreate in-memory WeakMap provenance. Fingerprints use exact insertion-order JSON, never sorted reconstruction. Successful calls without an emitted fingerprint remain a documented instrumentation gap; no fingerprint is guessed from a local schema.
