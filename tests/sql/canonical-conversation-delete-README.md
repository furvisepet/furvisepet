## Design and dependency audit

`canonical_ask_origin_message_id` copies only the existing canonical UUID. It has no message FK: it is evidence, never execution authority. `intelligence_source_message_id` retains its existing ON DELETE SET NULL FK and all noncanonical behavior. The new CHECK requires an origin exactly for canonical rows. Existing canonical status, owner, pet, origin, source type and span stay immutable. Inserts still require the privileged writer, a live owned USER source/owned pet and matching pending append or lifecycle authority. No entire transcript is copied.

The migration locks care rows and copies only the origin coordinate. A temporary, exact-copy-only timestamp predicate is replaced before commit; no trigger is disabled. Its final version exempts only the exact live-FK detachment after physical parent absence. All other content updates still touch `updated_at`. A final constraint trigger checks the post-BEFORE-trigger row too. The absence lookup is VOLATILE and SECURITY DEFINER so it sees the same command's deletion and cannot confuse RLS invisibility with absence. No role/JWT/GUC/depth flag grants detachment.

The current SQL snapshot and TypeScript `sourceSemanticsSnapshot` use the permanent origin, retaining the exact old sourceMessageId and updatedAt. Existing payload strings, digests, claims, receipts and classifications are not rewritten. `read_ask_source_semantics` retains its exact-current-snapshot equality and completeness logic. `readCorrectionRelevance` still rejects missing/changed/wrong-scope evidence. `persist_ask_source_semantics` deliberately keeps the claim's live FK from the nullable live care link; a new replacement after deletion therefore stamps a new care version without trying to reference the deleted message. Its serialized evidence still names the permanent origin. Claim live-link nulling is tightened to physical parent absence plus exact equality of all other fields.

`canonical_ask_replace_safe` retains every current graph/derived-state exclusion and terminal append-receipt/span match, but compares permanent origin coordinates. `is_canonical_ask_source` retains isolation using the permanent origin as well as surviving capabilities. Capability mint/execute, source/assistant locking, source freshness, target version, terminal replay, pending failure and REMOVE logic are unchanged. A deleted UUID cannot pass the required live-source mint/confirm checks. Inventory triggers are untouched; actual deletion and claim/care live-link updates can invalidate inventory.

Other application readers (`supabase` memory lookup, Today/effective-history, stored-read and retrieve-context suppression, conversation detail saved-status lookup) use the live reference to join existing messages. They need no permanent transcript reconstruction and remain unchanged. Ordinary care history still reads saved care itself. Legacy inference views have their original fixed column projection and exclude canonical care; the new column does not change their import fingerprints. Full occurrence inventory is included as `dependency-audit.json` with source hashes. Historical migration files are unchanged.

The HTTP DELETE handler remains unchanged: authentication/UUID/idempotent gate, owned-conversation lookup, service RPC, 503 on RPC error, otherwise 204. A new repeated request with no conversation returns 404; if a concurrent deletion occurs after owned lookup, RPC false still returns idempotent 204. This is documented/tested current behavior, not native concurrency proof. Detail/message routes return 404 and list omits the deleted row. Offline route IO and idempotency persistence are fixture seams; no UI/live/PostgREST proof is claimed.
